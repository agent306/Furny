## Deviations / concerns for the controller
1. `extract_words(keep_blank_chars=True)` instead of the spec's literal `False`. Brief test requires the word `"SCALE 1:100"` whole (and T29 expects `scaleNote.text == "SCALE 1:100"`); with `False` pdfplumber returns `SCALE` and `1:100`. Far-apart text still splits (x_tolerance). `extra_attrs=["size"]` is used for horizontal text only: for rotated glyphs pdfminer reports per-glyph size, which shatters words into letters.
2. Rotated text: default `extract_words` reads CCW-rotated text reversed (`TXET LACITREV`), so non-upright chars get two extra filtered passes (CCW: `char_dir_rotated="btt"`, CW: `"ttb"`); all map to `angle=90`. Diagonal text counts as upright (pdfminer's flag) -> angle 0.
3. Rect edges: every rect/curve contributes its edges as `VSeg` (spec: "each converted to segments"), even when only filled, with width = the graphics-state linewidth (a fill-only rect inherits whatever width was last set). Dark-filled rects also yield a `VPolygon`; I additionally emit a polygon for dark-filled curve paths with >= 3 points (filled triangles/L-shaped walls), which the brief only states for rects. Beziers are flattened into 8 chords; missing/pattern fill colour counts as not dark. Luminance: gray/RGB (Rec.709 weights)/CMYK.
4. Not changed: `requirements.txt` (no new runtime deps; pypdf already in dev group). `classify_pdf_page`/`extract_vector_page` re-parse the PDF with pdfplumber per call (no cache); callers (T9/T29) should classify once per page.

## Fix round 1 (commit below; files: vision/app/pipeline/pdf.py, vision/tests/test_pdf.py)
1. PDFium lock: confirmed in the pypdfium2 README ("Incompatibility with Threading": PDFium is inherently not thread-safe). A module-level `_PDFIUM_LOCK` (threading.Lock) is held for the whole `_open_pdfium` body, which every PDFium call (page count, page size, render, crop-box lookup) goes through. Never nested. Tests: `test_concurrent_pdfium_use_is_serialised` (8 threads x 5 iterations of count/render/size, no errors, correct shapes), `test_pdfium_lock_is_held_while_pdfium_is_used` (spy asserts the lock is held when PdfDocument is constructed and released afterwards).
2. CropBox alignment: `extract_vector_page` now shifts every segment, polygon and word box by the crop origin. The offset is computed from PDFium's MediaBox/CropBox (CropBox clipped to MediaBox) and `/Rotate`, mapped into the rotated frame, plus pdfplumber's `page.bbox` top-left (pdfplumber keeps the MediaBox origin, so a MediaBox not starting at (0,0) was also misaligned; found while testing). I did not use pdfplumber's own cropbox: its value is not rotated for /Rotate 180 (verified, would be off by 40 pt). Tests: `test_cropbox_repro_from_review` (the reviewer's repro: rect now at (10,10)); `test_vector_coords_align_with_render_under_cropbox_and_rotation` (3 crops x 4 rotations, checks the polygon pixels in the actual render are black and the pixels just outside white); `test_mediabox_with_nonzero_origin_aligns` (4 rotations x with/without CropBox). Segments/words use the same mapping; the rotation tests assert on polygons, words/segments share `to_px`.
3. Stale width: shapes with `stroke` false contribute no segments at all (their outline is invisible and the width is stale); dark fill still yields the `VPolygon`. Stroked/`B` rects keep their 4 edges with the real width. This is a change from deviation 3 (fill-only rects used to emit edges); updated `test_vector_coords` and `test_vector_fill_colour_rule` accordingly. New test `test_unstroked_shapes_do_not_inherit_stale_line_width` (`5 w … S` then a fill-only rect: only one 5.0-wide segment; S, B and f variants). object_count is unchanged (still lines + rects + curves).
4. Error mapping narrowed: the body of `_open_plumber_page` is no longer inside a blanket `except Exception`. Only pdfplumber's own calls (open, page lookup, `.lines/.rects/.curves`, word extraction, object count) run under `_pdfplumber_errors()`, which maps `PDFPasswordIncorrect` -> `pdf_encrypted`, anything else -> `corrupt_file` and logs the original exception at WARNING (logger `furny.vision.pdf`, exc_info). Our own conversion code now propagates real bugs (test `test_internal_bugs_are_not_reported_as_corrupt_file` monkeypatches `_add_object` to raise RuntimeError and asserts it is not turned into corrupt_file).
